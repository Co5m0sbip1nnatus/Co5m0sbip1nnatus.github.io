# What LoRA Fixed, What It Broke: Fine-Tuning a Prompt-Injection Detector Against Camouflaged Attacks

**TL;DR.** Few-shot injection detectors catch overt attacks but miss ones camouflaged in a document's own vocabulary. I fine-tuned Llama 3.1 8B with QLoRA to close that gap. Camouflage detection improved, but static detection dropped: a catastrophic-forgetting trade-off. A four-way hyperparameter sweep failed to remove it, and I argue it structurally cannot, because plain SFT has no term that preserves existing capabilities. An OR-ensemble of the few-shot and fine-tuned detectors routes around the problem entirely.

| Detector | Static | Camouflage | False positives | F1 |
|---|---|---|---|---|
| Few-shot (control) | 100% | 52.5% | 12.5% | 0.836 |
| Fine-tuned (best single) | 90 to 95% | 60 to 65% | 12.5 to 15% | 0.844 |
| **Ensemble (few-shot OR fine-tuned)** | **100%** | **82.5%** | 22.5% | **0.901** |

Full notebook with all code, training logs, and per-run artifacts: [notebook link](https://github.com/Co5m0sbip1nnatus/camouflage-injection-finetuning).

## 1. The problem: detectors that only catch attackers who announce themselves

Pai (2026, [arXiv:2605.22001](https://arxiv.org/abs/2605.22001)) showed that injection detectors are calibrated on payloads that announce themselves ("IGNORE ALL PREVIOUS INSTRUCTIONS"). Rewrite the same malicious goal in the target document's professional register, a technique the paper calls domain-camouflaged injection, and detection collapses: 93.8% to 9.7% on Llama 3.1 8B. Llama Guard 3 catches zero. The paper names this the Camouflage Detection Gap (CDG).

The paper's only attempted mitigation is few-shot augmentation, which partially works on strong models and fails on small ones. What nobody had tried: actually fine-tuning the detector on camouflaged examples. That is the gap this experiment fills, and since the authors released their task bank and payload generator, I could build directly on their setup.

## 2. The one decision that mattered: controlled comparison

Before any GPU time, I committed to one rule: this is not a paper reproduction, it is a controlled comparison. Same model (Llama 3.1 8B), same detection prompt, same parser, same metrics harness, same **fixed** test set. The only thing that changes between arms is the method: few-shot prompting versus LoRA fine-tuning. Whatever delta shows up is then attributable to the method and nothing else.

![Experimental design: controlled comparison](/assets/img/posts/what-lora-fixed-what-it-broke/I1.png)

The data pipeline: 200 tasks across 5 domains, each yielding a benign sample, a static injection (template appended), and 3 camouflage variants generated by an attacker LLM (gpt-4o-mini) and scored for similarity to the clean document (ACS). Two design choices carry most of the weight here. First, the split is by task_id, so all samples derived from one document land on the same side; a row-wise split would scatter near-duplicate variants across train and test and quietly inflate every number. Second, the test set keeps only the highest-ACS camouflage per task: evaluation is pinned to the hardest, best-blended variant, and the same 120 samples (40/40/40) are reused for every method in this post. Full rationale for each choice is in Appendix A.

## 3. Fine-tuning: what it fixed, and what it broke

Setup in three lines: 4-bit QLoRA (the 8B base frozen, rank-16 adapters on the attention projections, 6.8M trainable parameters, 0.08% of the model), trained to generate the same "VERDICT: INJECTED/CLEAN" output the few-shot detector produces, with a proper loop: task-level train/val split, cosine schedule with warmup, gradient clipping, best-validation checkpointing, early stopping. Hyperparameters start at LoRA convention midpoints and get swept later rather than assumed optimal (Appendix A).

![Training history: epoch-by-epoch train and validation loss, with the epoch-2 best-validation adapter marked and early stopping at epoch 4](/assets/img/posts/what-lora-fixed-what-it-broke/I2.png)

The loop did its job visibly: train loss kept falling (1.07 to 0.28) while validation bottomed out at epoch 2 and rose after, so early stopping cut the run and the epoch-2 adapter was kept. Textbook overfitting, caught by the machinery built to catch it.

Then the evaluation. Camouflage detection rose from 52.5% to 60% (a re-evaluation pass on different hardware read 65%; see the noise box below). But static detection fell from 100% to 95%. The detector got better at the subtle attacks and quietly stopped catching some of the obvious ones. That is catastrophic forgetting in miniature, and it turned the project from "report an improvement" into "understand a trade-off".

## 4. The sweep: four hypotheses, four failures

If a trade-off appears, the reflex is to tune it away. I swept one factor at a time, each config changing exactly one field of the default so the effect is attributable to that factor, with the selection rule fixed in advance: among runs keeping static at or above 95%, pick the highest camouflage rate, false positives as tiebreaker, differences under 5 points treated as ties.

- **variants1**: train on only the best camouflage variant per task, rebalancing classes to 160/160/160. Hypothesis: the static drop comes from camouflage (480 samples) dominating training.
- **epochs3**: cap training at 3 epochs. Hypothesis: less total training, less forgetting.
- **lowlr** (1e-4): smaller steps stay closer to the original weights.
- **r8**: half the adapter capacity, a lighter touch on the base model.

![Sweep comparison table](/assets/img/posts/what-lora-fixed-what-it-broke/I3.png)

![Every single model trades static for camouflage; the ensemble does not](/assets/img/posts/what-lora-fixed-what-it-broke/I4.png)

All four failed the selection rule. Not one config returned static to 100%, and two actively backfired. Rebalancing (variants1) landed at 87.5% static with camouflage back at the few-shot level, despite achieving the **lowest validation loss of any run**. And epochs3 was the surprise: camouflage crashed to 30%, worse than not fine-tuning at all. My reading is that shortening the epoch cap also compresses the cosine schedule, so the model stops in an awkward middle state where it has adjusted its output behavior but not yet learned the discrimination the extra data was supposed to teach.

> **Measurement noise, quantified.** With 40 test samples per attack type, one sample is 2.5 points. Re-evaluating the identical adapter after a pod migration shifted camouflage by 5 points (greedy decoding is not bit-reproducible across GPUs). A full retrain of the same config in earlier experiments shifted static by 12.5 points. So single-run differences under roughly 10 points are not conclusive here, and validation loss ranked configs differently than task metrics did. Every comparison in this post therefore uses the shared test set, and small gaps are called ties.

## 5. Diagnosis: why hyperparameters cannot fix this

Four independent levers targeting four different mechanisms, all failing the same way, suggests the problem is not the lever settings. I read it in three layers.

**Data size** limits precision (the noise box above) but is not the cause: more data would sharpen the measurement, not remove the trade-off.

**Distribution narrowness** is closer. The base model's injection judgment comes from a very broad pretraining distribution; my training set is 5 domains of one document style with one attacker's camouflage. Fine-tuning on a narrow slice does not surgically add a skill, it pulls the whole decision boundary toward that slice, and some static detections fall off the far edge. This is why rebalancing failed: 160/160/160 is still the same narrow slice.

**The objective itself** is the root. Plain SFT minimizes loss on the new data, and nothing in that objective says "keep what you already knew". Static-detection ability is not represented in the loss, so the optimizer will happily spend it to buy train-loss reduction. Catastrophic forgetting here is not a bug in my configuration; it is the specification of the method. Which means the fix has to change the objective or the composition, not the knobs: replay data, a KL penalty toward the base model, or, cheapest of all, not forcing one model to do both jobs.

## 6. The ensemble: routing around the trade-off

I already had two detectors with complementary strengths sitting on disk. The few-shot detector catches every static attack; the fine-tuned one catches more camouflage. So: flag INJECTED if **either** flags. No new training, no new inference, just a different combination of predictions already saved.

![Ensemble comparison table](/assets/img/posts/what-lora-fixed-what-it-broke/I5.png)

Static detection is back at 100% by construction. The surprise is camouflage: 82.5%, far above either detector alone. The reason is in the overlap:

![Which detector catches which camouflage attack](/assets/img/posts/what-lora-fixed-what-it-broke/I6.png)

Few-shot catches 21 of 40 camouflage samples, the fine-tuned model 24, but they share only 12. Fine-tuning did not strengthen the signals few-shot already used; it learned partially different ones, which is exactly when an OR-combination pays. The honest cost is false positives, which also union: 12.5% to 22.5%. In a security setting where a missed injection costs more than a false alarm, that is usually an acceptable trade, but it is real and would need calibration in deployment (for example, requiring agreement on low-stakes documents).

Where this goes next, in order of what I would run first: multi-seed reruns of the top configs to put error bars on everything; replay-based fine-tuning that mixes broad-distribution and static-injection data into training, attacking the diagnosis through composition; KL-regularized fine-tuning, attacking it through the objective; held-out-domain evaluation (train on four domains, test on the fifth) to separate memorization from transfer; and adaptive attacks that generate fresh camouflage against the ensemble itself, because a defense evaluated only on yesterday's attacks is a resume line, not a result.

## Appendix A: design choices and rationale

**Experiment level**

| Choice | Rationale |
|---|---|
| Controlled comparison, not reproduction | The goal is isolating the effect of the method. Fixing test set, model, prompt, and harness makes any delta attributable to fine-tuning. Matching the paper's absolute numbers is neither needed nor attempted. |
| Split by task_id, domain-stratified | Samples from one task share the same source document. A row-wise split scatters near-duplicates across train/test (leakage). The train/val split inside training uses the same principle (GroupShuffleSplit). |
| Test keeps best-ACS camouflage per task | Highest similarity to the clean document means the hardest, best-blended attack. Evaluation is pinned to the worst case, and the fixed 120-sample set is shared by every method. |
| Train keeps all 3 camouflage variants | The few-shot arm does not train, so train-set composition cannot bias the comparison; the fine-tune arm gets maximum data. The variants1 sweep config tests the cost of this choice. |
| Attacker gpt-4o-mini, detector local 8B | The detector must be local because it is the fine-tuning target. The attacker only generates data; a small API model is sufficient and cheap (about $0.12 for 600 payloads). |
| 4-bit quantization (QLoRA) | Fits 8B training on a single 24GB GPU. NF4 storage with bf16 compute is the standard recipe. |

**Training level**

| Choice | Rationale |
|---|---|
| r=16, alpha=32, lr=2e-4, q/v projections | Midpoints of LoRA convention (r 8 to 32, lr 1e-4 to 3e-4). Treated as starting points, not optima: r and lr are both swept. |
| Generative target ("VERDICT: ..."), same prompt as baseline | Adding a classification head would change the comparison object. Identical prompt and output format keep "only the method differs" true. |
| Epoch ceiling 5 + early stopping (patience 2) | The data decides when to stop instead of a fixed count. In run 1 this selected the epoch-2 adapter and cut the run at epoch 4. |
| Per-epoch validation, cosine schedule with warmup, gradient clipping | Train loss alone cannot detect overfitting; warmup avoids unstable early steps; clipping caps rare gradient spikes. |
| Best-validation checkpointing | The final epoch may already be overfit; the kept adapter is the one with the lowest validation loss. |
| Seeds fixed across python/numpy/torch/cuda | Each library holds an independent RNG; fixing one leaves nondeterminism in the others. |

## Appendix B: environment and reproducibility

RunPod, single RTX 3090 (24GB), PyTorch 2.8 + CUDA 12.8, transformers/peft/bitsandbytes at versions pinned in the notebook. Base model meta-llama/Llama-3.1-8B-Instruct in 4-bit NF4. Each run saves its config, training history, best adapter, metrics, and raw predictions to a timestamped folder; completed runs are skipped on re-execution, so the notebook is re-runnable top to bottom. One caveat worth repeating from the noise box: results were produced across a mid-project GPU migration, and greedy decoding is not bit-reproducible across hardware, which is itself a small lesson in what "reproducible" means in practice.
